# when-where backend

A small FastAPI service with exactly one real route:
`GET /api/destinations/top10`. It's the first place in this project where
the frontend talks to a backend, rather than reading a static JSON file
straight off GitHub.

## Why this exists

Everything in `data/processed/OVERARCHING_TRIP_SCORE_BY_COUNTRY.json`
(UNESCO, Michelin, price level) is a fixed number per country — it
doesn't know what month you're traveling in. Weather does. This API adds
weather as a fourth, date-resolved input: given a trip's `start_date` and
`end_date`, it works out which calendar month(s) the trip falls in
(day-weighted, so a trip spanning two months isn't just credited to
whichever one it starts in), looks up each candidate country's weather
for those months, and combines it with the three static scores into one
ranked top 10.

See `app/scoring.py` and `app/data_loader.py`'s docstrings for the actual
formulas and data sources — this README is the how-it-fits-together
version.

## What it does NOT do

- No scoring pipeline work of its own. It reads the same
  `data/processed/*.json` files `data/scripts/*.py` already produces —
  one source of truth, no duplicated logic.
- No database. Everything's loaded into memory once at startup from
  files already in this repo.
- `departure_country` is accepted as a query param and echoed back in
  the response, but doesn't affect ranking yet — reserved for a future
  distance/flight-time score. Don't be surprised that changing it doesn't
  change the results; that's intentional for now, not a bug.
- No traveler-profile weighting yet. The `interest` value the frontend's
  search form collects (hiking/beaches/food & culture/nightlife) isn't
  sent to or used by this API yet — today's weather-score formula in
  `scoring.py` is a single equal-weighted default for everyone. A natural
  next step is letting `interest` change how the six raw weather factors
  are weighted (a hiking trip cares about rain very differently than a
  beach trip).

## Local dev

This project uses one shared venv at the repo root (see the root
`README.md`), not a separate one inside `backend/` — activate that first,
then install this directory's deps into it:

```
source ../venv/bin/activate   # from backend/; run ../venv/bin/python -m venv ../venv first if it doesn't exist yet
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then:

```
curl "http://localhost:8000/api/destinations/top10?start_date=2026-07-05&end_date=2026-07-15"
```

Interactive docs (auto-generated by FastAPI from the Pydantic models in
`app/main.py`): `http://localhost:8000/docs`.

## Deploying to Render

This needs an **always-on web service**, not Vercel's Python serverless
functions — the whole point is loading `data/processed/*.json` into
memory once and reusing it across requests, which a serverless cold
start would defeat. Render's free tier fits (it does spin down after
~15 min idle, so the first request after a quiet period is slower, but
it's a much smaller reload than a serverless cold start).

Manual setup (Render dashboard → New → Web Service):

- **Root Directory:** `backend`
- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- **Health Check Path:** `/health`

`render.yaml` in this directory has the same config as a Blueprint, if
you'd rather use Render's "New Blueprint Instance" flow — note Render
looks for `render.yaml` at the repo root by default for auto-detection,
so you may need to point it at `backend/render.yaml` explicitly (or move
a copy to the repo root) depending on Render's current UI.

## CORS

`app/main.py` allows `https://travel.iesepulveda.com`,
`http://localhost:5173` (Vite dev), and `http://localhost:4173` (Vite
preview) by default. Override with the `ALLOWED_ORIGINS` env var
(comma-separated) for a branch preview domain or anything else, without a
code change.

## Frontend wiring

The frontend reads the API's base URL from `VITE_API_BASE_URL` (see
`frontend/.env.local.example`) — `http://localhost:8000` locally via
`.env.local` (gitignored), `https://when-where.onrender.com` in
production/preview builds via the committed `frontend/.env.production`
(not a secret, just this service's public URL — see that file's own
comment for why it's committed instead of left to a Vercel dashboard
env var).
